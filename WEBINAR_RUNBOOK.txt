2. THEORY TO SAY (MINUTES 2-6)
-------------------------------
How testing began
 - Early software: developers checked their own work; "testing" meant running the program and looking.
 - Testing became a separate discipline: testers write cases, run them by hand, record results, file defects.
 - Manual testing is still the best tool for exploration, usability, "does this feel right", and anything new.

What good manual testing looks like (say these four things)
 1. A test case: title, preconditions, numbered steps, expected result.
 2. Test data written down (which account, which card, which promo code).
 3. Results recorded per run: pass / fail / blocked, plus evidence (screenshot, order number).
 4. Defects filed with steps to reproduce, expected vs actual, environment.

Why it stops scaling
 - Same flows every release: checkout, login, search. Humans get slower, bored and inconsistent.
 - Multiple browsers x devices x releases multiplies the work.
 - Regressions slip through when time is short.
 -> Automation takes over the repetitive, stable, high-value flows. Humans keep exploration.

4. PAIN POINTS OF MANUAL REPETITION (MINUTES 11-13)
---------------------------------------------------
Say, looking at your notes sheet:
 - One flow, one browser, one dataset took minutes. A release has dozens of flows across browsers.
 - Results live in a sheet; evidence is a number you typed. Nothing is replayable.
 - The second time you do it, you skip steps. The tenth time, you stop looking.
Transition: "So we script it."

6. WHEN LOCATORS CHANGE: THE AUTOMATION PAIN POINT (MINUTES 17-21)
-------------------------------------------------------------------
Open the CHANGED URL (?v=2) in a normal browser tab next to the baseline. Say: "Spot the difference."
There is none visible except the small badge "UI version 2 (locators changed)". Same look, same text.
Under the hood: ids were renamed, e.g. #open-cart -> #cart-toggle, #nav-account -> #account-link.
Real-world causes: a redesign, a framework upgrade, a generated-class change, a developer "cleaning up" ids.

Run the same script against ?v=2 WITHOUT healing (local, so it fails fast and clearly):
  npm run test:v2
Observed in rehearsal: "2 failed", waiting for locator('#nav-account') and locator('#cart-count').
Talking point: "Nothing is broken for a user. The product works. The test is red. This is a false failure,
and somebody now spends an hour finding out that it was only a renamed id."
Quantify it: dozens of tests x frequent UI changes = maintenance becomes a job of its own.

7. SELF-HEALING ON AUTOMATE (MINUTES 21-25)   *** THE KEY SEGMENT ***
-----------------------------------------------------------------
Concept (20 seconds): Self-Heal detects when a locator no longer matches, finds the intended element using
historical context and AI signals (text, role, position, attributes), continues the test, and records what it
healed so you can update the script.

Run (cloud, ?v=2):
  npm run bstack:v2
Expected IF self-heal is enabled on the account: both tests pass, and the session shows healed locators.
Show: Automate dashboard -> the build -> the session -> the Self-Heal information (healed steps and the new locators).
Then show the follow-up: apply healed locators back to the script (via MCP or a generated PR for SDK users) so
the suite is fixed permanently, not just patched at runtime.

12. BACKUPS (WHAT TO DO WHEN SOMETHING BREAKS LIVE)
---------------------------------------------------
 A. GitHub Pages is down or slow: run the site locally with python3 -m http.server 8123 inside the website folder, and point
    the local tests at it with SITE_URL=http://localhost:8123/index.html npm test. This works for local runs only, because
    BrowserStack cloud cannot reach localhost without a tunnel.
 B. Self-heal is still red on the day: show the recorded healed run (recording or screenshots from rehearsal) and the doc page,
    and say you are showing a recording and why. Do not improvise a fix live.
 C. Automate is slow or queues: show the previous build in the dashboard (video and logs) while the new one starts.
 D. Credentials or auth errors: show the pre-recorded run, then fix after the session.
 E. Test Companion is slow: show the pre-generated test cases and script, and run the script with npm run bstack.
 F. A flaky assertion: re-run once. If it repeats, switch to the recording. Never edit a test live in front of the audience.
 G. Old accounts or orders appear on the site: clear site data, or open a fresh window.
 H. Total network loss: slides and recorded demos only. You can still deliver the story.

13. DOS AND DON'TS
------------------
DO
 - Rehearse the whole 30 minutes twice with a timer, including the ?v=2 self-heal run.
 - Keep one idea per segment and end each with a one-sentence takeaway.
 - Say what you are about to run before you press enter, and what you expect.
 - Show failures honestly. The red ?v=2 run is the story, not an embarrassment.
 - Keep attention on outcomes: false failures, time saved, stability.
DON'T
 - Don't claim self-healing is magic. It recovers locator drift. It does not fix wrong assertions or real bugs.
 - Don't claim generated tests need no review.
 - Don't show your BrowserStack access key. Keep it in environment variables only.
 - Don't debug a failure live for more than 30 seconds. Switch to the backup.
 - Don't leave stale instructions on screen. The commands in sections 5 to 7 and section 15 are the current ones.
 - Don't run the whole manual flow twice live. The second time adds nothing.

14. QUICK ANSWERS FOR Q AND A
-----------------------------
 - Does self-heal hide real bugs? It only substitutes a locator when the intended element is still there, and it records every
   heal for review. Real behaviour and assertion failures still fail.
 - Do we still need manual testing? Yes: exploration, usability and new features. Automation takes the repetitive regression.
 - Do I have to rewrite my suite? No. Self-heal is a capability setting (selfHeal: true) plus the account-level BrowserStack AI setting.
 - Is the generated code ours? Yes. It is plain Playwright you can edit and commit.
 - Which frameworks? This demo uses Playwright (JavaScript). The Self-Heal docs also cover Selenium and Cypress.
